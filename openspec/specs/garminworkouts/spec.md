## Purpose

## Entities

### GarminTypes

> `garminworkouts\garmin\garmintypes.py`

Service responsible for fetching, processing, and synchronizing Garmin workout, activity, event,
golf, and strength exercise type definitions from the Garmin API into local configuration files.

**Relationships:**

- extends GarminApi (Inherits HTTP communication capabilities from GarminApi base class)

### StepType

**Properties:**

| Name | Type | Description |

## Requirements

### Requirement: GarminTypesValidation

The system SHALL validate GarminTypes according to these rules:
- Type dictionaries must be valid Python dict literals that can be located and updated via regex in source files
- File paths for type output must be writable and their parent directories must exist or be creatable

#### Scenario: SyncAllGarminTypes
- **GIVEN** A valid Garmin API session and local source files containing type dictionaries
- **WHEN** updateGarmin() is called
- **THEN** All workout, activity, event, golf, and strength types are fetched and written back into the local
files

#### Scenario: FetchAndPersistWorkoutTypes
- **GIVEN** A Garmin API endpoint returns a list of workout type items
- **WHEN** get_types() calls process_workout_types() for a given name
- **THEN** Each item's fields are extracted and the corresponding type dictionary in the target file is updated

#### Scenario: FetchAndPersistActivityTypes
- **GIVEN** A Garmin API endpoint returns activity type data
- **WHEN** get_activity_types(file_path) is called
- **THEN** Activity types are processed and written to the specified file

#### Scenario: FetchAndPersistEventTypes
- **GIVEN** A Garmin API endpoint returns event type data
- **WHEN** get_event_types(file_path) is called
- **THEN** Event types are processed and written to the specified file

#### Scenario: FetchAndPersistGolfTypes
- **GIVEN** A Garmin API endpoint returns golf club type data
- **WHEN** get_golf_types(file_path) is called
- **THEN** Golf types are processed in two passes and written to the specified file

#### Scenario: GenerateStrengthExerciseTypeFiles
- **GIVEN** A local map of strength exercise categories and exercises exists
- **WHEN** get_strength_types() is called
- **THEN** Python generator functions and test functions are written to their respective output files for each
exercise

#### Scenario: UpdateTypeDictionaryInSourceFile
- **GIVEN** A source file contains a named Python dictionary literal and a new dictionary string is provided
- **WHEN** update_type_dict(file_path, dict_str, type_dict) is called
- **THEN** The existing dictionary value in the file is replaced with the new dict_str using regex substitution

#### Scenario: ResolveUnitToAPICode

### Requirement: DurationValidation

The system SHALL validate Duration according to these rules:
- Duration string must contain a recognized unit suffix (ppm, m, km, cals, reps, w) or a time separator (':') or be empty for lap-button
- Numeric portion of duration must be parseable as a float
- Distance display: values >= 100 are shown in meters, values < 100 are shown in kilometers

#### Scenario: ResolveDurationTypeFromString
- **GIVEN** A Duration with a string containing a known unit suffix

- **THEN** Returns the mapped Garmin duration type string (e.g., 'heart.rate', 'distance', 'calories', 'reps',

#### Scenario: ResolveTimeDurationType

#### Scenario: ResolveLapButtonDurationType

#### Scenario: ExtractNumericValueFromDurationString

- **THEN** Returns None

#### Scenario: ConvertTimeDurationToSeconds
- **GIVEN** A Duration whose string is in time format
- **WHEN** to_seconds() is called
- **THEN** Returns the total number of seconds as an integer

#### Scenario: FormatDurationValueForDisplay
- **GIVEN** A numeric value and a duration type string
- **WHEN** get_string() is called
- **THEN** Returns a human-readable string with the appropriate unit suffix

### Requirement: PaceValidation

The system SHALL validate Pace according to these rules:
- Pace in seconds must be at least 20 (enforced floor in to_seconds)
- vVO2 in seconds must be between 0 and 999 inclusive
- to_pace() requires pace to contain a ':' character (i.e., be a time-formatted string)

#### Scenario: ConvertPaceToSecondsWithFloor
- **GIVEN** A Pace instance with a time string value
- **WHEN** to_seconds() is called
- **THEN** Returns the number of seconds represented by the pace string, with a minimum value of 20

#### Scenario: ConvertPaceToSpeed
- **GIVEN** A Pace instance with a valid time string
- **WHEN** to_speed() is called
- **THEN** Returns speed in meters per second as 1000.0 divided by the pace in seconds

#### Scenario: CalculateAdjustedPaceWithVVO2
- **GIVEN** A Pace instance with a time-formatted string and a valid vVO2 value between 0 and 999 seconds
- **WHEN** to_pace(vVO2, diff) is called
- **THEN** Returns an adjusted speed based on vVO2 and the diff offset in meters

#### Scenario: CalculatePaceWithoutVVO2
- **GIVEN** A Pace instance with a time-formatted string and no vVO2 argument
- **WHEN** to_pace() is called
- **THEN** Uses the pace's own seconds as the base speed and applies the diff adjustment

#### Scenario: RejectToPaceOnNonTimePace
<!-- openlore-test: tags=regression (auto) -->
- **GIVEN** A Pace instance whose string does not contain ':'
- **WHEN** to_pace() is called
- **THEN** Raises ValueError with message 'Pace must have time'

#### Scenario: RejectInvalidVVO2Range
<!-- openlore-test: tags=regression (auto) -->
- **GIVEN** A Pace instance and a vVO2 value outside 0–999 seconds
- **WHEN** to_pace(vVO2) is called
- **THEN** Raises ValueError indicating vVO2 must be between 0 and 1000 seconds

### Requirement: PowerValidation

The system SHALL validate Power according to these rules:
- FTP must be between 0 W and 999 W (exclusive)
- Resolved absolute power must be between 0 W and 4999 W (exclusive)
- Power string ending in 'w' (case-insensitive) is treated as absolute watts
- Power string ending in '%' (case-insensitive) is treated as a percentage of FTP
- Power string with no suffix is treated as an FTP multiplier

#### Scenario: ConvertAbsoluteWattValue
- **GIVEN** A Power instance with a value ending in 'w' (e.g. '250w') and a valid FTP
- **WHEN** to_watts() is called
- **THEN** Returns the numeric watt value parsed from the string, rounded to nearest integer

#### Scenario: ConvertPercentageOfFTP
- **GIVEN** A Power instance with a value ending in '%' (e.g. '85%') and a valid FTP
- **WHEN** to_watts() is called
- **THEN** Returns FTP multiplied by the percentage divided by 100, rounded to nearest integer

#### Scenario: ConvertFTPMultiplier
- **GIVEN** A Power instance with a plain numeric value (e.g. '0.85') and a valid FTP
- **WHEN** to_watts() is called
- **THEN** Returns FTP multiplied by the numeric value, rounded to nearest integer

#### Scenario: RejectOutOfRangeFTP
<!-- openlore-test: tags=smoke,regression (auto) -->
- **GIVEN** A Power instance and an FTP value outside [0, 999]
- **WHEN** to_watts() is called
- **THEN** Raises ValueError describing the valid FTP range

#### Scenario: RejectOutOfRangeResolvedPower
<!-- openlore-test: tags=smoke,regression (auto) -->
- **GIVEN** A Power instance whose resolved absolute wattage falls outside [0, 4999]
- **WHEN** to_watts() is called
- **THEN** Raises ValueError describing the valid power range

#### Scenario: ComputePowerZonesForCyclingAndRunning
- **GIVEN** A running FTP Power (rftp) and a cycling FTP Power (cftp), each expressed with a 'w' suffix
- **WHEN** power_zones() is called
- **THEN** Returns zone boundary fractions, running zone floors, cycling zone floors, and structured zone data
for both CYCLING and RUNNING sports
- **AND** Cycling zone data includes zone6Floor and zone7Floor derived from the zone list
- **AND** Running zone data sets zone6Floor and zone7Floor to 0.0
